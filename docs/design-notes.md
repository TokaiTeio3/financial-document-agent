# 设计思路与技术取舍

## 证据组织优先于上下文扩展

金融长文本问答的难点通常是主体、期间、指标、单位和适用条件分散在不同页面，而非单纯缺少上下文长度。项目首先统一文档解析与来源标识，再通过文档定位、页面检索和局部证据整理构造回答依据。

PDF 按物理页转换为 Markdown，TXT 与 HTML 进入相同的文档目录。公司名称、简称、标题和年份用于限定检索范围，指标与数字锚点用于定位页面和片段。模型接收带来源的证据，避免直接依赖整份文档的非结构化阅读。

## 词法检索的适用范围

公司名、年份、比例、条款原文等具有较强的词面信号。BM25 配合实体别名、关键词锚点和相邻页扩展，可以在不部署 embedding 模型与向量数据库的条件下完成检索，并直接分析排序依据。

这一选择也存在限制：问题大幅改写、通过品牌间接指代公司，或需要推断跨文档关系时，词面匹配可能漏召回。查询规划和补检索用于缓解这类问题，但没有完整对照实验可证明词法检索在所有任务中优于语义检索。

## 模型决策与程序执行的边界

模型负责业务语义、证据选择和公式识别；程序负责算术、格式化及确定性校验。金融计算中，即使公式执行正确，错误的收入范围、基准年份或单位仍会产生错误结论，因此计算结果必须与证据来源共同审计。

AST 白名单限制任意代码执行风险，但不等同于完备沙箱。部署时仍需控制表达式规模、执行资源、异常和访问权限。引用编号及 Schema 校验也只能保证结构，不能单独证明引用支持结论。

## 动态补证与规则复杂度

不同领域设置证据预算与裁决路径，可以减少无关上下文，并针对缺失条件或操作数补检索。代价是规则之间产生耦合：一次结果可能同时受文档绑定、窗口截取、领域提示和答案修复影响，单个样例修复并不代表同类问题全部解决。

评估应同时观察文档与页面召回、约束覆盖、操作数完整性、结构化输出、Token 和延迟。比赛总分及单次运行开销反映整体结果，尚不足以归因某一启发式的独立收益。后续优化需要对照实验和分类回归，而非仅按最终答案调参。

## 真实失败对设计的约束

- 页面召回与证据完整性分开评估。表格证据需要保留表头、目标行和合计口径，不能仅检查页码是否命中。
- 同题事实共享与独立任务上下文分开设计。隔离选项能够减少干扰，但可能使计算节点缺少已验证的公共操作数。
- 基准冲突与公式执行分开处理。正文近似值和表格精确值均可能有来源依据，应记录精度与题干指代关系。
- 局部支持与全局一致性分开核验。量词、主体范围和互斥结论不能仅凭某个相似片段裁决。

具体样例见 [真实失败分析](bad-cases.md)。题级 FactStore、完整表格闭包、精度冲突裁决和统一的选项冲突检查仍是待验证的改进方向。

`scripts/build_version_locked_ensemble.py` 与提交打包工具属于历史辅助工具，保留用于回归及审计。正式冷启动入口为 `generate_answer.py` / `run_reproduce.py`，历史答案拼接不计为新一次推理结果。

## 赛后工程整理

使用 LangGraph 将准备、规划、worker 和汇总组织为显式状态图，领域检索通过 LangChain 工具封装，并配套流式前端。并行节点采用追加式 reducer 合并结果和 Token，公开轨迹记录节点、调用理由、工具参数与证据摘要，不展示模型私有思维链。

单次检索可回答是任务拆分目标，不是召回保证。当前封装尚未提供完整事实共享、自动计算节点、持久化恢复及鉴权。后续扩展应由缺失操作数、冲突事实和资源预算驱动，保持模型决策与确定性工具之间的明确边界。
