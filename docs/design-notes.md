# 设计笔记：从规则密集到显式状态

## 我当时先解决什么

比赛需要从原始长文档生成格式固定的答案。许多问题不是“这段话是什么意思”，而是“这个数属于谁、哪一年、哪种口径”。所以最早的投入是解析、文档定位和证据来源，而不是换更大的上下文。

PDF 按物理页转换为 Markdown，TXT 和 HTML 也进入同一文档目录。保留文档和页码，再建立公司名、简称、标题与年份的定位线索。在页级 BM25 之后，用问题中的数字、指标和短语锚点截取片段。模型看到的是有来源的证据，而不是整本年报。

没有 embedding 是这个实现的约束和选择，不是“词法检索胜过所有语义检索”的结论。它让我不用部署向量模型，可以直接检查排序原因；当问题改写很大或公司通过品牌被间接提及时，它也容易漏掉文档。

## 哪些逻辑适合交给程序

四则运算、单位换算、输出格式和引用编号校验都适合确定性实现。模型负责识别问题要算什么、哪些数是操作数，再把变量和计算逻辑提交给受限执行器。执行结果还要回到证据与业务口径上检查。

执行器不是完备的沙箱。AST 白名单减少任意代码风险，仍需要表达式规模、资源耗时和异常约束；部署时不能因为“没有 eval”就忽略拒绝服务风险。更重要的是，公式执行正确也救不了错误的分母或错误的收入范围。

## 哪些规则开始让我犹豫

竞赛版按领域设置检索数量和字符预算，还加入缺证补检索、跨选项数值修复和不同语义的裁决逻辑。每条规则都有具体来由，但组合之后就难回答“这个答案到底由什么决定”。单个 badcase 修好，也不代表整类问题已解决。

我没有做足以证明每条规则收益的完整消融。报告中的总分和一次运行开销可以说明系统结果，不能说明某个启发式单独贡献了多少分。公开这个项目时，应该把这条边界保留下来。

`scripts/build_version_locked_ensemble.py` 和提交打包工具是历史辅助工具，保留用于理解回归测试与审计，不是公开 Demo 的运行依赖。正式冷启动复现入口是 `generate_answer.py` / `run_reproduce.py`，不能把历史答案拼接当作新一次推理。

## 重新实现时的边界

重构版只有四个主节点：准备问题、规划、子问题 worker、汇总。Max 只负责拆分；Flash 从领域检索工具中选一个，拿到结果后做结构化压缩。独立子问题用 `Send` 派发，并行返回的证据、结果和 Token 用 reducer 追加合并。

这比竞赛版容易观察，但也会失去能力。单次检索不一定能拿齐所有操作数；压缩可能丢失限定条件；多个 worker 还没有共享的事实存储。计算工具虽已定义，主图没有自动执行计算节点。README 需要直说这些，而不是把两版能力拼在一起。

把“一次检索可回答”当作 Planner 的目标，是为了控制流程，不是对召回的保证。下一步若要增加循环，我会让它由缺失操作数和冲突事实触发，并设置次数与 Token 上限。

## 可观测不等于展示全部思考

前端应该告诉用户：当前节点是什么、选了哪个工具、查询内容是什么、返回了哪些证据、为什么使用这些证据，以及消耗了多少 Token。这些信息足以调试流程，不需要展示模型的私有思维链。

Token 从服务返回的 usage 统计，不能把未返回 usage 的失败请求默认为免费。现在的统计适合观察一次正常运行，尚不等同于计费审计。

## 我会优先补的三件事

1. 题级 FactStore：按主体、期间、指标、口径和单位保存带来源的事实；worker 读取所需子集，避免彼此缺操作数。
2. 表格与来源跨度：按表头、目标行和合计行构造闭包；跨页 overlap 保留每段的真实页码，而不是只标中心页。
3. 计算节点和小型回归集：补齐操作数后才允许执行，将来源冲突、精度冲突与语义冲突分别测试。

这些仍是改进计划，没有把它们写成已完成的功能。持久化恢复、限流、鉴权和多租户属于后续部署工作，这次公开版本先服务于个人项目展示和本地实验。
